# Классификатор запросов в ИИ-саппорте: полная техническая спецификация

> Исследование Alex (deep research, 2026-07-20). Проектный референс для этапа 6 (подсистема классификации kremzaPay-бота). Сохранено из чата.

## 1. Что решает классификатор

На каждый запрос — структурированное решение, не одна метка:

```json
{
  "intent": "refund_request",
  "category": "billing",
  "scope": "in_scope | out_of_scope | off_topic | unsafe",
  "sentiment": "negative",
  "urgency": "high",
  "language": "ru",
  "confidence": 0.87,
  "secondary_intent": "cancel_order",
  "entities": {"order_id": "A-12345"},
  "reasoning": "..."
}
```

**Интент и категория — разные оси.** Категория → куда идти за знаниями и кому эскалировать; интент → какой сценарий запускать. Смешивание осей в плоский список — типовая ошибка, ломается после ~30 меток.

## 2. Таксономия — фундамент

1. Иерархия: 5–12 категорий × 5–15 интентов; каскадная классификация (сначала категория, потом интент) точнее на больших таксономиях.
2. Интенты взаимоисключающие и наблюдаемые (действие пользователя, не внутренний процесс).
3. Каждому интенту: определение + 5–10 реальных примеров + контрпримеры («это НЕ refund_request, если про статус уже оформленного возврата — это refund_status»).
4. Обязательные служебные классы: `other_in_scope`, `out_of_scope`, `chitchat`. Без «прочего» модель насильно запихивает всё в ближайший класс.
5. Таксономию строят из данных (кластеризация 500–2000 реальных обращений), не из головы; живёт месячным циклом разбора `other_in_scope`.

## 3. Три метода классификации

### 3.1 LLM-классификатор (zero/few-shot)
Промпт: список интентов с определениями и примерами + история + запрос → строгий JSON.
Приёмы: поле `reasoning` ДО полей решения; structured output/enum; классификация с учётом истории; query rewriting перед классификацией в многооборотных диалогах; каскад «категория → интент» при >30 интентах.
Плюсы: старт без данных, понимает перефразировки. Минусы: латентность/цена, некалиброванная уверенность.

### 3.2 Эмбеддинги + kNN/центроиды
10–50 примеров на интент → векторы; kNN (k=5–10) или центроиды; **два порога**: `t_accept` (выше — метка принята) и `t_oos` (ниже максимальной близости — out-of-scope); между ними — серая зона → LLM или уточнение. Пороги подбираются на отложенной выборке.
Плюсы: миллисекунды, новые интенты добавлением примеров, расстояние = сигнал OOS. Минусы: тонкая семантика при схожей лексике.

### 3.3 Дообученная малая модель
DeBERTa-голова или SetFit (работает с 8–30 примеров/класс). Самый точный/дешёвый в рантайме на устоявшейся таксономии; минусы: пересбор при изменении таксономии, softmax требует калибровки, отдельная OOS-стратегия обязательна.

### 3.4 Каскад (рекомендация)
```
Слой 0: правила/регулярки («оператор», «человек») → сразу handoff   ~0 мс
Слой 1: эмбеддинги+kNN (t_accept / t_oos)                           ~10–30 мс
Слой 2: LLM-классификатор (JSON, reasoning, secondary_intent)       ~0.5–2 с — только серая зона (10–30%)
Слой 3: уточняющий вопрос или эскалация
```

## 4. Out-of-scope / off-topic

Несколько независимых сигналов, любой уводит с основной ветки:
1. Явный класс OOS/chitchat в таксономии (для fine-tuned — hard negatives, близкие к домену).
2. Порог расстояния в эмбеддинг-пространстве.
3. Retrieval-сигнал: ничего выше порога → знаний нет, что бы ни сказал классификатор.
4. LLM-проверка скоупа в сером диапазоне.

Разные ветки реакции:

| Тип | Реакция |
|---|---|
| out_of_scope | честный отказ + перенаправление, не угадывать |
| chitchat | 1–2 дружелюбные реплики + возврат к делу; счётчик подряд |
| unsafe | шаблонный отказ, текст не идёт в LLM, сессия помечается |
| other_in_scope | общая RAG-ветка; копится → новые интенты |

## 5. Уверенность и калибровка

- Softmax ≠ вероятность; лечится temperature scaling (минимизация ECE).
- Вербализованная уверенность LLM смещена (любит 0.8–0.95): просить **категорию** (high/medium/low с определениями) и превращать в число по статистике фактической точности; либо logprobs.
- Пороги — матрица по интентам: порог = f(цена ошибки, качество модели на интенте). where_is_my_order — 0.6; refund_request — 0.9+/подтверждение/эскалация.
- Комбинированная уверенность = минимум нормализованных сигналов (классификатор, реранкер, groundedness).

## 6. Сложные случаи

Несколько намерений (secondary_intent, обработка по очереди) · смена интента по ходу диалога (интент — атрибут реплики) · эмоция поверх интента (sentiment/urgency понижают порог эскалации) · имплицитные запросы («пришёл разбитый товар») · код-свитчинг и опечатки (аугментации в данных).

## 7. Оценка качества

Офлайн: золотой набор 300–1000 размеченных запросов (10–20% OOS/chitchat), версионируется; метрики macro-F1, precision/recall OOS (recall OOS — главная цифра безопасности), confusion matrix, ECE.
Онлайн: доля эскалаций/«не понял»/other_in_scope по неделям; дрейф расстояний; еженедельная выборочная переразметка; каждая эскалация с меткой оператора — бесплатный размеченный пример.
Петля (ежемесячно): собрать other_in_scope + ошибки → кластеризовать → обновить таксономию → прогнать золотой набор → выкатывать только при улучшении.

## 8. Чек-лист внедрения

1. Двухуровневая таксономия из кластеризации; определения+примеры+контрпримеры; служебные классы обязательны.
2. Каскад: правила → kNN (t_accept/t_oos) → LLM (история, reasoning, JSON) → уточнение/эскалация.
3. Query rewriting в многооборотных диалогах.
4. OOS минимум по двум независимым сигналам; разные ветки out_of_scope/chitchat/unsafe/other_in_scope.
5. Калибровка уверенности; пороги на интент по цене ошибки.
6. Финальная уверенность = слабейшее звено.
7. Золотой набор с первого дня; macro-F1 + OOS-recall + ECE на каждое изменение; месячный цикл таксономии.
